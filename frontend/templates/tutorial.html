What this system does

  • Identifies at-risk students — it computes the best- and worst-case participation mark each student can still reach, and flags anyone whose best case cannot clear the module's pass threshold (Algorithm 1).
  • Monitors class performance — the dashboard and cohort table show the current class average, the class size and who needs attention.
  • Plans for the cohort — it proposes the marks a student needs on the assessments still to be written (Algorithm 2) and searches for a spread of assessment weights that moves the class average towards a target you choose (Algorithm 3).

Every model comes from Van der Merwe et al. (2018b) and runs in backend/algorithms/; the pages only present their output.

The workflow, step by step

  1. Create a module — a code, a name and the pass threshold that decides at-risk flags.
  2. Define the assessment plan — add the assessments that make up the participation mark and give each one a weight (they should total 100%).
  3. Add students and marks — one anonymised code per student, then a mark per assessment (blank = not written yet). Use Enter marks to capture a whole class in one pass.
  4. Read the dashboard — class average, at-risk count and class size. The at-risk list and each student's page explain the indicators, including the participation plan.
  5. Plan the cohort — set a target class average and a weight range per assessment, then let the optimiser find the closest achievable spread. Weights can never be zero.

Before you start

This is a research prototype for ITRI671. It holds its data in memory only: everything resets when the app restarts, and nothing is written to disk. Please do not enter real student names, student numbers, ID numbers or e-mail addresses — use anonymised codes and the bundled simulated dataset (backend/data/sample_data.csv).
